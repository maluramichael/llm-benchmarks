# 2026-11-02: PC RTX 3090 24 GB

One run of the standard benchmark. Results table and prompt are in the [README](../README.md). This is an extra model outside classes S to XL and F: Ornith-1.5-122B, a Mixture of Experts model that does not fit into 24 GB. The experts stay in RAM, only the rest and a cache run on the GPU. Prompts and settings are the same as in the [run from 2026-10-26](2026-10-26-pc-rtx-3090-24gb.md), and the logic and concurrency tests are the same as in the [run from 2026-10-30](2026-10-30-pc-rtx-3090-24gb.md).

Preparation: not freshly restarted (about 4 hours uptime at the start), desktop apps stayed open and used about 1.7 GB VRAM together with the desktop. The monitor is on the RTX 3090. Sysmem Fallback Policy set to "Prefer No Sysmem Fallback", TdrDelay 10, TdrDdiDelay 20. No GPU driver reset during the whole run. This model cannot run completely on the GPU, which the standard prompt would record as "does not fit". It was measured anyway, and the 100% GPU rule of the context test does not apply to llama.cpp here.

## Finding the best settings

All with llama.cpp build 12001, 16k context, two warm requests with 8,192 tokens. The table shows the second request.

| Settings | Prompt processing tok/s | Generation tok/s | VRAM (GB) |
|:---------|-----------------------:|-----------------:|---------:|
| `--cpu-moe` | 91 | 10.3 | 7.4 |
| `--cpu-moe --moe-cache-mib 8000` | 110 | 10.1 | 15.4 |
| `--cpu-moe --moe-cache-mib 12000` | 119 | 11.7 | 19.4 |
| `--cpu-moe --moe-cache-mib 15000` | 125 | 13.1 | 22.4 |
| `--cpu-moe --moe-cache-mib 15000 --load-mode none` | 210 | 23.4 | 22.4 |
| Same plus `--spec-type draft-mtp --spec-draft-n-max 3` | 206 | 17.5 | 23.7 |
| `--n-cpu-moe 38 --load-mode none` | 233 | 13.9 | 21.9 |

`--load-mode none` makes the biggest difference: it almost doubles generation, and the first request is as fast as the second (with mmap the first request reads at about 46 to 58 tok/s). llama.cpp suggests this itself in its log when tensors are overridden to the CPU. MTP slows this setup down and leaves less than the 1.5 GB reserve free, so it was not used for the full run. The full run uses a 14 GB cache instead of 15 GB, so the reserve stays free up to 64k context.

## Tests

<a id="llama-cpp-ornith-1-5-122b-q4-k-m"></a>
### llama.cpp 0.8.0-dev (build 12001), Ornith-1.5-122B Q4_K_M (Extra)

- **Engine + version:** llama.cpp 0.8.0-dev, build 12001 (commit eb4e244be), llama-server, official release win-cuda-13.4-x64
- **Model (exact tag):** ornith-1.5:122b-q4_K_M (Ollama library file, 75.84 GB, without vision projector)
- **Quantization:** Q4_K_M
- **Class:** Extra (Mixture of Experts, 125B parameters, 256 experts with 8 active per token, does not fit into VRAM)
- **Max context:** 65,536 (capped on purpose, higher steps not tested because of watchdog crashes at 128k and 256k with other models on this card)
- **Cold load (s):** 74.73
- **TTFT cold (s):** 77.61
- **TTFT warm (s):** 38.01
- **TTFT with cache (s):** 2.70
- **Prompt processing tok/s:** 216
- **Generation tok/s:** 22.5
- **Generation tok/s at max context:** 21.2 (prompt processing 210)
- **Notes:** llama-server with `-ngl 99 -fa on --fit off -np 1 --cpu-moe --moe-cache-mib 14000 --load-mode none`, base context 16k, median of 3 runs. Uses 21.4 GB VRAM at 16k and 22.6 GB at 64k (both including about 1.7 GB for the desktop), plus about 68 GB of RAM mapped for the GPU, which is the host buffer for the experts and not an overflow. In the prompt cache test, 7,695 of 8,210 tokens came from the cache, TTFT 2.70 s instead of 37.95 s. Context steps (prompt processing / generation tok/s): 8k 202 / 22.1, 16k 204 / 22.3, 32k 205 / 21.7, 64k 202 / 20.8 in the first pass, so speed hardly depends on context. No llama-bench run, because llama-bench does not support `--moe-cache-mib`.

### Ollama 0.40.13, Ornith-1.5-122B Q4_K_M (Extra)

- **Engine + version:** Ollama 0.40.13
- **Model (exact tag):** ornith-1.5:122b-q4_K_M (75.84 GB plus 0.91 GB vision projector)
- **Quantization:** Q4_K_M
- **Class:** Extra (Mixture of Experts, 125B parameters, 256 experts with 8 active per token, does not fit into VRAM)
- **Max context:** not measured (ollama ps shows 28% GPU, so the context test ended at the first step)
- **Cold load (s):** 81.23
- **TTFT cold (s):** 84.14
- **TTFT warm (s):** 32.71
- **TTFT with cache (s):** 2.51
- **Prompt processing tok/s:** 251
- **Generation tok/s:** 13.3
- **Generation tok/s at max context:** not measured
- **Notes:** Own `ollama serve` with one slot and f16 KV cache, base context 16k, median of 3 runs. Ollama splits whole layers (72% CPU, 28% GPU according to ollama ps) and has no setting for an expert cache in its standard configuration. That gives similar values to llama.cpp with `--n-cpu-moe 38`: prompt processing is a bit faster than with the cache setup, generation is much slower. VRAM reaches 24.2 of 24.6 GB, so the 1.5 GB reserve is not kept, there was still no GPU reset. The model sets `draft_num_predict 3`, so Ollama uses MTP (about 53 percent of drafted tokens accepted in one sample). The first load took 94.8 s (TTFT 110.9 s). In the prompt cache test, 7,699 of 8,210 tokens came from the cache, TTFT 2.51 s instead of 32.06 s. In the third run the answers ended early (166 and 111 tokens), so generation there is measured over fewer tokens.

The same 65 German questions as in the [run from 2026-10-30](2026-10-30-pc-rtx-3090-24gb.md#logic-and-coding-test), with llama.cpp and the settings above.

|:------|:--------:|---------------:|------------:|------------:|:------:|:-------:|:----------:|:-----:|:-----:|:-----:|:----------:|:-----------:|
| Ornith-1.5-122B Q4_K_M (Extra) | off | 64 | 397 | 5,575 | 5/5 | 6/6 | 17/17 | 9/9 | 2/2 | 7/7 | 7/8 | 11/11 |

Without thinking, Ornith gets the best score of all models so far in that mode (Qwen3.8 27B: 60), and only Qwen3.8 27B with thinking is better (65). The only question it fails in both modes is PHP's `"abc" == 0`: it answers `true`, which was correct before PHP 8. With thinking it even mentions the change in PHP 8, but keeps the old answer. Thinking adds two errors: it misspells "Bananenernte" while counting letters, and one written Python function has a wrong indentation and does not run.

The same test as in the [run from 2026-10-30](2026-10-30-pc-rtx-3090-24gb.md#concurrent-requests), with 8 slots and the settings above. Values per cell: total generation tok/s / generation per request tok/s / seconds to first token (median).

| Model | 1 concurrent | 2 concurrent | 4 concurrent | 8 concurrent | Seconds for 8 requests | VRAM (GB) |
|:------|:------------|:------------|:------------|:------------|----------------------:|---------:|
| Ornith-1.5-122B Q4_K_M (Extra) | 16 / 22 / 4.96 | 17 / 13 / 9.88 | 17 / 6 / 19.79 | 15 / 3 / 36.18 (max 41.65) | 137.9 | 21.9 |

Total throughput does not grow with more requests, it stays at about 15 to 17 tok/s. Requests only share the same speed, and the wait for the first token grows from 5 to 36 seconds. On this card the model is only useful for one request at a time.

## Summary

The best setup is llama.cpp with experts in RAM, a 14 GB GPU cache and `--load-mode none`: 22.5 tok/s generation, 216 tok/s prompt processing and 64k context with hardly any slowdown, while Ollama processes prompts slightly faster (251 tok/s) but generates at only 13.3 tok/s. Notable are the strong answers for a model running mostly on the CPU (64 of 65 logic and coding questions without thinking, more than Qwen3.8 27B without thinking), the load time of about 75 seconds, and the lack of any scaling with concurrent requests. Nothing crashed and there was no GPU reset; context was capped at 64k on purpose, and the Ollama context test ended at the first step because the model cannot run 100% on the GPU.
